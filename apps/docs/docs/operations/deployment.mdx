# Deployment

The repository builds application images for GHCR and triggers Coolify through
GitHub Actions. API, worker, and simulator containers load runtime secrets from Infisical.
The checked-in configuration does not provision Coolify, DNS, TLS, or PostgreSQL.

## Images and networking

Build each image with the repository root as context.

| Application | Dockerfile                  | Internal port / behavior                                        |
| ----------- | --------------------------- | --------------------------------------------------------------- |
| API         | `apps/api/Dockerfile`       | `API_PORT`, default 5001; long-running server                   |
| Web         | `apps/web/Dockerfile`       | 80; static SPA with history fallback                            |
| Docs        | `apps/docs/Dockerfile`      | 80; static Docusaurus site                                      |
| Worker      | `apps/worker/Dockerfile`    | No listener; migrates, optionally promotes an admin, then exits |
| Simulator   | `apps/simulator/Dockerfile` | No listener; ongoing demo occupancy updates when enabled        |

The web Nginx configuration does **not** proxy `/api` and does not consume
`API_UPSTREAM`. Choose a browser-reachable API origin using the web image's
`VITE_API_URL` build argument, or configure an external proxy to route `/api`
when that argument is empty. Changing the argument requires rebuilding the web
image. Configure the external proxy for credentialed requests and unbuffered,
long-lived SSE connections. Validate cookie delivery for the selected domains.

The API image defaults to `TRUST_PROXY_HOPS=1` for the Coolify reverse proxy;
direct local runs default to `0`. This makes the approval-route limit
(`POST /api/admin/users/:id/approve`, 10 requests per minute) apply per client IP
instead of sharing the proxy's budget. Keep the
API port private so clients cannot bypass the trusted proxy. If the deployment
has additional proxies, set `TRUST_PROXY_HOPS` to the actual trusted hop count
and ensure the edge proxy replaces client-supplied forwarding headers. See the
[Express proxy guidance](https://expressjs.com/en/guide/behind-proxies/).
Clients sharing a public IP still share a budget. Counters are held in memory
per API process and reset on restart.

Set `WEB_ORIGIN` to the actual frontend origin and `BETTER_AUTH_URL` to the public
auth origin. Register the GitHub callback at
`BETTER_AUTH_URL/api/auth/callback/github` when the auth URL is an origin.
Docs uses the canonical domain in `apps/docs/docusaurus.config.ts`.

## Runtime secrets

API, worker, and simulator entrypoints require `INFISICAL_CLIENT_ID`,
`INFISICAL_CLIENT_SECRET`, `INFISICAL_PROJECT_ID`, and `INFISICAL_ENV`.
`INFISICAL_SECRET_PATH` defaults to `/api` for the API, `/worker` for the
worker, and `/simulator` for the simulator. Secrets are injected at process
startup; restart to load changes.

The API needs `PG_*`, auth configuration, and GitHub OAuth credentials. The
worker needs a database identity permitted to apply migrations. Optional
`ADMIN_EMAIL` names an account to promote to an approved administrator; the worker
needs no auth settings for this. See
[Environment Variables](../reference/environment-variables).

## Migration and administrator bootstrap

Run the worker against the intended database before starting application code
that needs new schema. It retries database connectivity up to 30 times, applies
the checked-in Drizzle migrations, optionally promotes the administrator, closes
the database pool, and exits. A failure exits nonzero.

The worker never creates accounts. If `ADMIN_EMAIL` matches an existing account,
the worker sets its role to `admin` and marks it approved. An account that is already an approved administrator is left unchanged. If
no account has that email yet, the worker logs a message and exits successfully;
have the administrator sign in with GitHub, then rerun the worker. Omit
`ADMIN_EMAIL` to run migrations only.

API containers do not migrate at startup. The deployment workflows publish the
worker image but do not run it or enforce migration-before-API ordering. Configure
that sequencing in the deployment environment.

### Approval column removal

Migration `0004_loud_jamie_braddock.sql` drops the obsolete unique constraint and
`user.approval_token`. It changes no approval or role values. Do not edit or
reapply historical migrations. Generation only reads the local schema/snapshots;
applying this migration is a separate deployment operation.

This destructive cleanup is an exception to the usual migration-before-API
order for an existing installation. The new API/worker/schema work against both
the old schema (unused nullable column present) and the new schema. Old API and
worker versions still select/write the column; old readiness also selects it,
so dropping it while they run breaks both requests and readiness.

Use a coordinated maintenance rollout: stop old web traffic, drain and stop all
old API/worker/seed processes, deploy the new API and bundled web, then run the
new worker to apply migration 0004 before reopening traffic. Alternatively,
replace every API/worker instance with this version while retaining the column,
then run the worker; do not send old web clients to the new API because the
administration contract has changed. A fresh installation can run all migrations
before starting the new applications. Development Compose's migration-first
startup is safe when the old stack has been stopped.

New readiness selects only the current ORM columns, so it can be ready before
the obsolete column is dropped; it is not proof that migration 0004 ran. Check
the worker outcome/migration history separately. Old readiness fails after the
drop. Do not roll back to an old image after dropping the column without a
separately reviewed schema restoration/forward fix; old tokens are gone, and
approval now uses user IDs. No application startup applies migrations.

## Demo simulator

The staging workflow publishes `ghcr.io/<owner>/cluster-map-simulator` when
selected by change detection; the main workflow excludes it. Configure a separate Coolify service using its
`staging` tag for a demo database, with no public port or HTTP health check.
Start it after migrations and demo seeding have completed.

The simulator image defaults to `NODE_ENV=production`, which the application
refuses when enabled. In the staging `/simulator` Infisical path, set
`NODE_ENV=development`, `SIMULATOR_ENABLED=true`, and the demo database's `PG_*`
connection settings. `INFISICAL_ENV` selects the secret environment; it does
not set `NODE_ENV`. Optional `SIMULATOR_*` settings control the user count,
tick interval, and action probabilities. Keep the simulator disabled against
production databases.

Build locally from the repository root:

```bash
docker build -f apps/simulator/Dockerfile -t cluster-map-simulator .
docker run --rm --network host --env-file .env cluster-map-simulator
```

The `.env` file must supply the Infisical bootstrap variables listed above.
Host networking reaches a locally published PostgreSQL port on Linux; for a
container network, use that network and configure a reachable database host.
The image runs compiled JavaScript as the non-root `node` user and handles
termination signals through the simulator's shutdown handler.

## Release behavior and verification

`staging.yml` and `main.yml` build selected images and trigger the corresponding
Coolify webhook. Production rebuilds from `main`; it does not promote the exact
staging image digest. The webhook's successful HTTP response is the final
automated check; workflows do not wait for application readiness. See
[CI/CD Implementation](../development-and-testing/CI-CD-implementation).

After deployment, verify:

1. The migration worker exits successfully.
2. `GET /api/health` returns `200` with `{ "status": "ok" }`.
3. `GET /api/health/ready` returns `200` with `{ "status": "ready" }`.
4. Account approval and GitHub sign-in work with the actual browser origin and
   cookies.
5. Cluster snapshots, SSE delivery, and reconnect recovery work through the proxy.
6. Database data persists across application replacement.

The API validates environment variables and creates Better Auth before listening.
`/api/health` checks process liveness only. `/api/health/ready` checks database
reachability, URL settings, and selected database tables; production requires HTTPS
web/auth URLs and an exact `WEB_ORIGIN` with no trailing slash. Readiness does not
query `two_factor`, validate layout, or prove occupancy freshness or successful
sign-in. Neither endpoint is a deployment gate in the workflows. API Docker
health checks use `/api/health` and the effective port recorded by the entrypoint.
Web/docs health checks only test static hosting. Use `/api/health/ready` as the
load-balancer traffic/readiness probe. The development Compose API probe deliberately
uses readiness so `web` waits for migrations and usable API configuration.

## Graceful shutdown

`SIGTERM` and `SIGINT` share one idempotent shutdown operation. Readiness becomes
false immediately and new application requests are rejected with `503`. The HTTP
listener stops accepting connections. Poll scheduling stops, all SSE responses
end, and their keepalive/revalidation scheduling and subscriptions are removed.
Already running ordinary HTTP requests, polls, probes, and session revalidations
are allowed to settle. Late poll/session results cannot write to closed streams
or restart timers. Once HTTP and owned background work drain, the API closes
its own process's PostgreSQL pool, flushes the logger, and exits `0`.

The overall deadline is `SHUTDOWN_TIMEOUT_MS` (default `10000`, integer range
`100`–`120000` milliseconds), including database close and log flushing. On expiry,
all tracked sockets (including idle/upgraded connections) are destroyed and the
process exits `1`, even if a database query or `pool.end()` never resolves. Cleanup
failures also exit `1`. The production logger writes synchronously, so forced exit
does not depend on an async stdout queue. Blocking event-loop or stdout operations
still require the container runtime's external kill deadline.

Configure the orchestrator termination grace period above the API deadline (for
example, 15 seconds for the default 10 seconds). Development Compose sets
`stop_grace_period: 15s` and launches `tsx watch` directly from the API directory,
so the container init forwards stop signals to the watcher, which relays them to
the API Node process. The watcher retains source reloads but force-kills its child
after five seconds; dev Compose therefore sets `SHUTDOWN_TIMEOUT_MS=4000` so the
API can enforce its own deadline first. The 15-second container grace period does
not extend the watcher's five-second limit. API shutdown does not stop the worker,
simulator, or a database server; these processes have separate ownership.

## Local development and recovery

`docker-compose.dev.yml` runs PostgreSQL, the migration worker, API, web, and docs,
with an optional simulator profile. It uses `Dockerfile.dev` without Infisical.
See [Local Development](../getting-started/local-development#run-everything-in-docker)
for startup, seeding, and reload behavior. Production uses the app Dockerfiles above.

Keep a record of healthy image references and a tested database backup/restore
procedure. Rollback requires selecting compatible earlier images in the deployment
environment. Automatic rollback and schema reversal are not implemented.
