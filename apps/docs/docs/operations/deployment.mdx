# Deployment

The repository builds application images for GHCR and triggers Coolify through
GitHub Actions. API and worker containers load runtime secrets from Infisical.
The checked-in configuration does not provision Coolify, DNS, TLS, or PostgreSQL.

## Images and networking

Build each image with the repository root as context.

| Application | Dockerfile               | Internal port / behavior                                       |
| ----------- | ------------------------ | -------------------------------------------------------------- |
| API         | `apps/api/Dockerfile`    | `API_PORT`, default 5001; long-running server                  |
| Web         | `apps/web/Dockerfile`    | 80; static SPA with history fallback                           |
| Docs        | `apps/docs/Dockerfile`   | 80; static Docusaurus site                                     |
| Worker      | `apps/worker/Dockerfile` | No listener; migrates, optionally creates an admin, then exits |

The web Nginx configuration does **not** proxy `/api` and does not consume
`API_UPSTREAM`. Choose a browser-reachable API origin using the web image's
`VITE_API_URL` build argument, or configure an external proxy to route `/api`
when that argument is empty. Changing the argument requires rebuilding the web
image. Configure the external proxy for credentialed requests and unbuffered,
long-lived SSE connections. Validate cookie delivery for the selected domains.

The API image defaults to `TRUST_PROXY_HOPS=1` for the Coolify reverse proxy;
direct local runs default to `0`. This makes the auth limit (10 attempts per
minute) apply per client IP instead of sharing the proxy's budget. Keep the
API port private so clients cannot bypass the trusted proxy. If the deployment
has additional proxies, set `TRUST_PROXY_HOPS` to the actual trusted hop count
and ensure the edge proxy replaces client-supplied forwarding headers. See the
[Express proxy guidance](https://expressjs.com/en/guide/behind-proxies/).
Clients sharing a public IP still share a budget. Counters are held in memory
per API process and reset on restart.

Set `WEB_ORIGIN` to the actual frontend origin and `BETTER_AUTH_URL` to the public
auth origin. Register the GitHub callback at
`BETTER_AUTH_URL/api/auth/callback/github` when the auth URL is an origin.
Docs uses the canonical domain in `apps/docs/docusaurus.config.ts`.

## Runtime secrets

Both API and worker entrypoints require `INFISICAL_CLIENT_ID`,
`INFISICAL_CLIENT_SECRET`, `INFISICAL_PROJECT_ID`, and `INFISICAL_ENV`.
`INFISICAL_SECRET_PATH` defaults to `/api` for the API and `/worker` for the
worker. Secrets are injected at process startup; restart to load changes.

The API needs `PG_*`, auth configuration, and GitHub OAuth credentials. The
worker needs a database identity permitted to apply migrations. Optional
`ADMIN_EMAIL` and `ADMIN_PASSWORD` bootstrap an approved administrator and also
require `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL`. See
[Environment Variables](../reference/environment-variables).

## Migration and administrator bootstrap

Run the worker against the intended database before starting application code
that needs new schema. It retries database connectivity up to 30 times, applies
the checked-in Drizzle migrations, optionally creates the administrator, closes
the database pool, and exits. A failure exits nonzero.

If the configured email already belongs to an approved administrator, the worker
keeps the existing account and password. If it belongs to any other account,
bootstrap fails; the worker does not promote or reset that account. Omit both
administrator credentials to run migrations only.

API containers do not migrate at startup. The deployment workflows publish the
worker image but do not run it or enforce migration-before-API ordering. Configure
that sequencing in the deployment environment.

## Release behavior and verification

`staging.yml` and `main.yml` build selected images and trigger the corresponding
Coolify webhook. Production rebuilds from `main`; it does not promote the exact
staging image digest. The webhook's successful HTTP response is the final
automated check; workflows do not wait for application readiness. See
[CI/CD Implementation](../development-and-testing/CI-CD-implementation).

After deployment, verify:

1. The migration worker exits successfully.
2. `GET /api/health` returns `200` with `{ "status": "ok", "db": "ok" }`.
3. `GET /api/health/ready` returns `200` with `{ "status": "ready" }`.
4. Password login, account approval, GitHub sign-in, and TOTP work with the actual
   browser origin and cookies.
5. Cluster snapshots, SSE delivery, and reconnect recovery work through the proxy.
6. Database data persists across application replacement.

`/api/health` checks connectivity only. `/api/health/ready` checks auth settings,
selected database tables, and auth initialization; production requires HTTPS
web/auth URLs and an exact `WEB_ORIGIN` with no trailing slash. Readiness does not
query `two_factor`, validate layout, or prove occupancy freshness or successful
sign-in. Neither endpoint is a deployment gate in the workflows. API Docker
health checks use `/api/health` and the effective port recorded by the entrypoint.
Web/docs health checks only test static hosting.

The public `/privacy` and `/terms` pages currently identify themselves as drafts
awaiting operator details and confirmation of deployment practices. Their presence
does not establish that release documentation is complete; see
[Privacy and Quality Requirements](../product/privacy-and-quality-requirements#public-policy-pages).

## Local development and recovery

`docker-compose.dev.yml` runs PostgreSQL only. Use
[Local Development](../getting-started/local-development) for the applications.
There is no checked-in full-stack Compose file or custom database Dockerfile.

Keep a record of healthy image references and a tested database backup/restore
procedure. Rollback requires selecting compatible earlier images in the deployment
environment. Automatic rollback and schema reversal are not implemented.
