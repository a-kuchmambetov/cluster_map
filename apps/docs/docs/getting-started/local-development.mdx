# Local Development

The repository includes the cluster map, authentication, administrator approvals,
PostgreSQL schemas, tests, and a Compose service for the development database.

## Prerequisites

- Node.js 24 is used by the API and web Dockerfiles and is a suitable local baseline.
- pnpm 11.5.2, matching the root package-manager configuration.
- Docker Compose for the local database, or an existing development PostgreSQL server.

## Install and configure

Run from the repository root:

```bash
pnpm install
cp .env.example .env
openssl rand -base64 32
```

Put the generated value in `BETTER_AUTH_SECRET`. Keep `API_PORT=5001`,
`BETTER_AUTH_URL=http://localhost:5001`, and `WEB_ORIGIN=http://localhost:5173`.
Set `VITE_API_URL=http://localhost:5001`; Vite has no API proxy.

Set `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` as well: API auth initialization
requires both even for password login and seeding. For local password-only
work, non-empty dummy values are sufficient. To exercise GitHub sign-in, use
real OAuth App credentials and callback
`http://localhost:5001/api/auth/callback/github`. See [Configuration](./configuration).

## Prepare the database

```bash
pnpm db:up
```

Wait for the DB to become healthy (`docker compose -f docker-compose.dev.yml ps db`), then run:

```bash
pnpm --filter @repo/api... build
pnpm db:migrate
pnpm db:seed
```

The filtered build makes the API and its shared `dist/` packages available.
Migrations create auth and Hive tables, including TOTP storage. Use `pnpm build`
when you also need the web and worker builds. The optional seed writes demo
accounts and occupancy to the configured database; use a local/demo database.
It refuses to run with `NODE_ENV=production` and is not a live simulation agent.

On a fresh seed, sign in with `demo-admin@example.test` or
`demo-member-1@example.test` and password `Demo-password-123!`. The administrator
can approve `demo-pending@example.test` from `/admin/users`. Existing demo accounts
retain their passwords and approval/role state when seeding again. Existing
positions are also preserved; rerunning the seed does not reset occupancy.

For an initial administrator without demo fixtures, set `ADMIN_EMAIL` and
`ADMIN_PASSWORD` in `.env`, then run `pnpm worker:dev`. This one-shot worker
migrates first and creates an approved admin if the email does not exist.
An existing approved admin is preserved; any other existing account causes
bootstrap to fail. Omit both credentials for migrations only.

## Start web and API

```bash
pnpm dev
```

| Service | URL with the walkthrough configuration | Behavior                                                 |
| ------- | -------------------------------------- | -------------------------------------------------------- |
| Web     | `http://localhost:5173`                | Login, registration, protected map, and admin approvals. |
| API     | `http://localhost:5001`                | Health, auth, cluster HTTP endpoints, and SSE.           |

The frontend calls `VITE_API_URL` directly. If Vite chooses another port, update
`WEB_ORIGIN` and restart the API. `pnpm dev` also runs the worker once, applying
migrations and optional admin bootstrap; it is not an occupancy simulator.

```bash
curl http://localhost:5001/api/health
curl http://localhost:5001/api/health/ready
```

A reachable database returns `200` with `{ "status": "ok", "db": "ok" }`.
An unavailable database returns `503` with
`{ "status": "degraded", "db": "unreachable" }`.

Readiness returns `200` with `{ "status": "ready" }` when auth configuration,
the selected schema checks, and auth initialization succeed; otherwise it returns
`503` with `{ "status": "not-ready" }`. It does not check all migrations or
complete a sign-in. See the [API Reference](../reference/api#get-apihealthready).

The web also serves `/privacy` and `/terms` without requiring sign-in. Both
currently display draft documents awaiting operator details and deployment confirmation.

## Start individual workspaces

```bash
pnpm --filter @repo/api dev
pnpm --filter @repo/web dev
pnpm start:docs
```

Docusaurus starts separately at `http://localhost:3000`; `pnpm dev` does not start
it. Use the API workspace command so relative `.env` and layout paths resolve.

## Live occupancy simulator

`apps/simulator` is an optional, demo-only process that creates synthetic users
with randomly combined names and emails and periodically has them take or free
seats. It writes directly to the database, so the map and SSE polling reflect
live changes.

First seed the database so clusters, rows, and positions exist:

```bash
pnpm --filter @repo/api... build
pnpm db:migrate
pnpm db:seed
```

Then enable the simulator in `.env`:

```bash
SIMULATOR_ENABLED=true
# SIMULATOR_USER_COUNT=20
# SIMULATOR_INTERVAL_MS=5000
# SIMULATOR_CLAIM_PROBABILITY=0.7
# SIMULATOR_RELEASE_PROBABILITY=0.3
```

Run it explicitly; it is not started by `pnpm dev` or `pnpm start`:

```bash
pnpm simulator:start
```

The simulator exits immediately if `SIMULATOR_ENABLED` is not `true` or if
`NODE_ENV=production`. It acquires a PostgreSQL advisory lock so only one
instance runs against a database at a time. Restarting reuses existing
`sim-member-*` identities and preserves their display names; it never releases
seats held by seed members or real users.

Stop it with `Ctrl+C` (SIGINT) or `SIGTERM`.

## Common checks

```bash
pnpm typecheck
pnpm lint
pnpm fmt:check
pnpm --filter @repo/api test
pnpm --filter @repo/api test:integration
pnpm --filter @repo/web test
pnpm --filter @repo/worker test
node --test scripts/deploy/*.test.mjs
pnpm build:docs
```

See [Testing and Simulation](../development-and-testing/testing-and-simulation)
for the optional DB-backed test and [Deployment](../operations/deployment) for
application images, runtime secrets, and migration ordering.

`pnpm db:down` runs `docker compose -f docker-compose.dev.yml down`, stopping
the development database without removing its named volume. `pnpm start` runs
workspace start scripts, including the built API and one-shot worker, Vite
preview, and the Docusaurus development server. For Vite preview, align
`WEB_ORIGIN` with its actual port.
