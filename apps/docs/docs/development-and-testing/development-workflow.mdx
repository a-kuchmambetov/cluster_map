# Development Workflow

Cluster Map is a pnpm workspace containing applications in `apps/` and reusable packages in `packages/`. Complete the [local development setup](../getting-started/local-development.mdx) before changing a workspace.

## Workspaces

| Workspace          | Purpose                                                             |
| ------------------ | ------------------------------------------------------------------- |
| `@repo/web`        | React and Vite frontend                                             |
| `@repo/api`        | Express API                                                         |
| `@repo/worker`     | One-shot migrations and optional administrator bootstrap            |
| `@repo/docs`       | Docusaurus documentation                                            |
| `@repo/db`         | Drizzle client, schema, and migration tooling                       |
| `@repo/errors`     | Shared application error type                                       |
| `@repo/types`      | Shared TypeScript types                                             |
| `@repo/validators` | Starter/example Zod schema; feature schemas are currently API-local |

## Common Commands

Run these commands from the repository root.

| Command           | Purpose                                                     |
| ----------------- | ----------------------------------------------------------- |
| `pnpm dev`        | Start web/API development and run the migration worker once |
| `pnpm build`      | Build every workspace except the documentation site         |
| `pnpm build:docs` | Build the documentation site                                |
| `pnpm typecheck`  | Run workspace type checks                                   |
| `pnpm lint`       | Run Oxlint from the repository root                         |

To work on one application, use a filter:

```bash
pnpm --filter @repo/web dev
pnpm --filter @repo/api dev
pnpm --filter @repo/docs start
```

The worker is also available through `pnpm worker:dev`, `pnpm worker:build`, and
`pnpm worker:start`. It exits after migrations and optional admin creation.
`pnpm dev` does not start Docusaurus; use `pnpm start:docs`.

## Git Flow

Project convention: commits and pull request titles follow [Conventional commits](https://www.conventionalcommits.org/en/v1.0.0/#summary).

Describe each pull request as one coherent change suitable for squash merging.

:::info[Development branches]

The documented branch convention uses four long-lived development branches:

- dev-api
- dev-web
- dev-db
- dev-docs

Create another branch for work outside these areas.

:::

Under this convention, keep the long-lived development branches after merging.
Repository settings, rather than these docs, control branch protection and deletion.

Development branches use the `dev-` prefix. Integrate through `staging` before
`main`; the checked-in workflows deploy those branches to their corresponding
environments.

## Suggested Change Flow

1. Confirm whether the behavior is implemented, proposed, or still an open decision.
2. Make the smallest change in the owning application or package.
3. Put cross-application types and validators in shared packages only when they are genuinely shared.
4. Run the relevant type check and build.
5. Update the documentation and [current status](../overview/current-status.mdx) when the public behavior or architecture changes.

GitHub Actions runs the checks described in
[Testing and Simulation](./testing-and-simulation.mdx) for pull requests to
`main` and `staging`. Deployment workflows run separately; see
[CI/CD Implementation](./CI-CD-implementation).
