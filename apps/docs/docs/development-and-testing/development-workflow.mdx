# Development Workflow

Cluster Map is a pnpm workspace containing applications in `apps/` and reusable packages in `packages/`. Complete the [local development setup](../getting-started/local-development.mdx) before changing a workspace.

## Workspaces

| Workspace          | Purpose                                       |
| ------------------ | --------------------------------------------- |
| `@repo/web`        | React and Vite frontend                       |
| `@repo/api`        | Express API                                   |
| `@repo/docs`       | Docusaurus documentation                      |
| `@repo/db`         | Drizzle client, schema, and migration tooling |
| `@repo/errors`     | Shared application error type                 |
| `@repo/types`      | Shared TypeScript types                       |
| `@repo/validators` | Shared Zod schemas                            |

## Common Commands

Run these commands from the repository root.

| Command           | Purpose                                                                                       |
| ----------------- | --------------------------------------------------------------------------------------------- |
| `pnpm dev`        | Start workspace development scripts in parallel                                               |
| `pnpm build`      | Build every workspace except the documentation site                                           |
| `pnpm build:docs` | Build the documentation site                                                                  |
| `pnpm typecheck`  | Run workspace type checks                                                                     |
| `pnpm lint`       | Invoke recursive workspace linting; coverage depends on the scripts exposed by each workspace |

To work on one application, use a filter:

```bash
pnpm --filter @repo/web dev
pnpm --filter @repo/api dev
pnpm --filter @repo/docs start
```

## Git Flow

All **Commits** and **Pull requests** must follow [Conventional commits](https://www.conventionalcommits.org/en/v1.0.0/#summary).

Pull request must be presented as description of one "big feature" (Squash Merge Request), rather than bunch minor of commits. Again, following Conventional commits.

:::info[Use this branches]

Next 4 branches are permanent and prefered for certain scope of features:
- dev-api
- dev-web
- dev-db
- dev-docs

For fetures out of this scope, new branch can be created.

:::

After successful Pull request this and other branches are not deleted and stored for task tracking purpose.

## Suggested Change Flow

1. Confirm whether the behavior is implemented, proposed, or still an open decision.
2. Make the smallest change in the owning application or package.
3. Put cross-application types and validators in shared packages only when they are genuinely shared.
4. Run the relevant type check and build.
5. Update the documentation and [current status](../overview/current-status.mdx) when the public behavior or architecture changes.

Automated tests are not configured yet. Until they are, do not describe a test suite as an enforced project check. See [Testing and Simulation](./testing-and-simulation.mdx).
