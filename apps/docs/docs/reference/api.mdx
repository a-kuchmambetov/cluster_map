# API Reference

## Current status

The Express application exposes these map and health endpoints:

- `GET /api/health`
- `GET /api/health/ready`
- `GET /api/clusters`
- `GET /api/clusters/:clusterNumber/layout`
- `GET /api/clusters/:clusterNumber/occupancy`
- `GET /api/clusters/:clusterNumber/config-validation`
- `GET /api/clusters/:clusterNumber/events` — SSE stream

The API mounts its router at `/api`. It enables JSON request parsing and credentialed CORS; allowed origins are described in [Configuration](../getting-started/configuration#cors-and-environment-mode).

Cluster endpoints require a Better Auth session cookie and a currently approved account. Health checks remain public. Missing or expired sessions return `401`; revoked or unapproved accounts return `403`. Cluster responses use `Cache-Control: no-store`.

## Authentication endpoints

Auth responses use `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.
Successful JSON operations below return `200`. Browser `POST`, `DELETE`,
`PATCH`, and `PUT` requests must use the trusted origin. The browser sends
credentials for HTTP requests and SSE.

| Method and path                 | Input                                                         | Result / access                                                                                        |
| ------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `GET /api/auth/session`         | Session cookie                                                | `{ user }` for a currently approved account.                                                           |
| `POST /api/auth/logout`         | Session cookie                                                | Invalidates the session, clears cookies, returns `{ message: "Logged out" }`.                          |
| `GET /api/auth/sign-in/github`  | Optional `callbackURL` query, defaulting to the frontend root | Redirects to GitHub and sets OAuth cookies.                                                            |
| `GET /api/auth/callback/github` | Provider callback query and OAuth cookies                     | Delegates to Better Auth and forwards its redirect/cookies. New users still require approval.          |
| `GET /api/auth/pending-users`   | Approved admin session                                        | `{ users: [{ id, name, email, createdAt, approvalToken }] }`, ordered by creation time then ID.        |
| `GET /api/auth/users`           | Approved admin session                                        | `{ users: [{ id, name, email, role, approved, approvalToken, createdAt }] }`, ordered by name then ID. |
| `POST /api/auth/confirm/:id`    | Single-use approval token in `:id`; approved admin session    | Approves the account, clears its token, and returns `{ message }`. This parameter is not a user ID.    |
| `DELETE /api/auth/users/:id`    | User ID; approved admin session                               | `{ message: "User deleted" }`; self-deletion is rejected with `403`, missing users with `404`.         |

The public `user` shape is `{ id, name, email, emailVerified, image, role }`; role
is `user` or `admin`. Approval tokens appear only in
administrator listings and must not be exposed to ordinary viewers.

The Express auth limiter allows 10 requests per IP per 60 seconds across approval
requests. Session reads,
logout, GitHub redirects/callbacks, user listings, and user deletion are registered
before this limiter. Cluster routes have no separate rate limiter.

### Approval and deletion behavior

New GitHub accounts require administrator approval before session creation. Explicit non-redirect OAuth callback failures
are sent to `/login?error=github_access_denied` for a 403, or
`/login?error=github_sign_in_failed` for other statuses; Better Auth redirects
are forwarded as provided.

Deletion cascades to sessions, linked accounts, and Hive identity. A position referencing that Hive identity prevents deletion through
its restrictive foreign key. The API currently surfaces that database failure
as `500 INTERNAL_SERVER_ERROR`; it does not release seats automatically.

Existing SSE connections revalidate access every 20 seconds and close if
validation fails. The client checks its session after stream failures and stops
retrying on `401`/`403`.

The protected curl examples below need a session cookie. Sign in with GitHub in a
browser and copy the `better-auth.session_token` cookie into `cookies.txt`. The
demo seed accounts cannot sign in.

## Error envelope

Errors handled by the API error middleware use this JSON shape. Health and readiness failures and unregistered routes are exceptions described below:

```ts
type ApiErrorResponse = {
  ok: false;
  status: "fail" | "error";
  code:
    | "BAD_REQUEST"
    | "UNAUTHORIZED"
    | "FORBIDDEN"
    | "NOT_FOUND"
    | "CLUSTER_NOT_FOUND"
    | "CONFLICT"
    | "TOO_MANY_REQUESTS"
    | "VALIDATION_ERROR"
    | "INTERNAL_SERVER_ERROR";
  error: string;
  details?: unknown;
};
```

Auth and cluster routes can return `401 UNAUTHORIZED` or `403 FORBIDDEN`. Invalid/consumed approval tokens return `404 NOT_FOUND`; auth errors can also include `409 CONFLICT`. The auth rate limiter returns `429 TOO_MANY_REQUESTS`.

Example validation error:

```json
{
  "ok": false,
  "status": "fail",
  "code": "VALIDATION_ERROR",
  "error": "Validation error",
  "details": [
    {
      "path": "clusterNumber",
      "message": "Expected number, received nan",
      "code": "invalid_type"
    }
  ]
}
```

Common error-middleware responses:

| Condition                                             | HTTP status | Code                    |
| ----------------------------------------------------- | ----------: | ----------------------- |
| Malformed JSON request body                           |         400 | `BAD_REQUEST`           |
| Missing or expired session                            |         401 | `UNAUTHORIZED`          |
| Unapproved account or insufficient privileges         |         403 | `FORBIDDEN`             |
| Invalid or consumed approval token                    |         404 | `NOT_FOUND`             |
| Auth conflict                                         |         409 | `CONFLICT`              |
| Auth rate limit exceeded                              |         429 | `TOO_MANY_REQUESTS`     |
| Path parameter fails Zod validation                   |         422 | `VALIDATION_ERROR`      |
| Cluster number has no matching cluster in the config  |         404 | `CLUSTER_NOT_FOUND`     |
| Unexpected server error (e.g. occupancy source fails) |         500 | `INTERNAL_SERVER_ERROR` |

`status` is `"fail"` for 4xx codes and `"error"` for 5xx codes.

When `NODE_ENV=production`, `error` for 5xx responses is replaced with `"Internal server error"` and `details` is omitted. In other modes, the original message and `details` are returned and the server logs diagnostic information.

Unknown routes are an exception to this envelope: there is no catch-all JSON not-found middleware, so an unregistered path falls through to Express's default 404 response.

## Request validation

Path parameters are validated once by the shared `handler` wrapper. It passes Zod's parsed output to a typed controller context without mutating the HTTP request. Express 5 forwards validation and controller errors to the error middleware (validation failures surface as `422 VALIDATION_ERROR`). All `:clusterNumber` routes below use:

```ts
z.object({ clusterNumber: z.coerce.number().int().positive() });
```

A non-numeric, non-integer, or non-positive `clusterNumber` (e.g. `abc`, `1.5`, `0`, `-1`) fails this schema.

## `GET /api/health`

Checks PostgreSQL with `SELECT 1` and a two-second query timeout. It does not
verify migrations, authentication configuration, or occupancy freshness.
Use `/api/health/ready` for the additional checks described below.

### Request

The endpoint has no parameters, request body, or authentication requirement.

```bash
curl http://localhost:5001/api/health
```

### Success response

Status: `200 OK`

```json
{
  "status": "ok",
  "db": "ok"
}
```

If the database is unavailable or the check times out, the endpoint returns
`503` with `{ "status": "degraded", "db": "unreachable" }`, outside the normal
error envelope.

## `GET /api/health/ready`

Public application readiness check with no parameters or request body.

```bash
curl http://localhost:5001/api/health/ready
```

| Result                                                | HTTP status | Body                        |
| ----------------------------------------------------- | ----------- | --------------------------- |
| Checks pass                                           | 200         | `{ "status": "ready" }`     |
| Invalid URL settings, failed schema check, or timeout | 503         | `{ "status": "not-ready" }` |

Required auth environment variables are validated once at startup, and Better Auth
is created before the API listens. The readiness check requires
`WEB_ORIGIN` to be an exact origin (no path or trailing slash). In production,
both `WEB_ORIGIN` and `BETTER_AUTH_URL` must use HTTPS. It selects declared columns
with `LIMIT 0` from `user`, `session`, `account`, `verification`, `cluster`,
`row`, `position`, and `user_hive_info`.
The database phase has a three-second timeout. Failures use the body above,
outside the normal error envelope.

This is a partial readiness check: it does not query `two_factor`, inspect
migration history, validate the layout, check occupancy freshness, or exercise
GitHub sign-in. It does not apply migrations. The API Docker health check
still targets `/api/health`; deployment workflows do not call either endpoint.

## `GET /api/clusters`

Returns the list of clusters known to the layout config. Used to render a cluster picker; it does not report occupancy or vacancy counts.

### Request

No parameters or request body. An approved session is required.

```bash
curl -b cookies.txt http://localhost:5001/api/clusters
```

### Success response

Status: `200 OK`

```json
{
  "clusters": [
    { "id": "c1", "number": 1, "label": "Cluster 1" },
    { "id": "c2", "number": 2, "label": "Cluster 2" },
    { "id": "c3", "number": 3, "label": "Cluster 3" }
  ]
}
```

| Field    | Meaning                                                                         |
| -------- | ------------------------------------------------------------------------------- |
| `id`     | Stable machine identifier for the cluster, from the config.                     |
| `number` | User-facing cluster number; also the `:clusterNumber` used in the other routes. |
| `label`  | UI caption for the cluster.                                                     |

This list comes from the layout config file and does not reflect occupancy
freshness. A malformed or unreadable config file returns
`500 INTERNAL_SERVER_ERROR`. The authentication guard still requires a working
database even though the list itself makes no occupancy query.

## `GET /api/clusters/:clusterNumber/layout`

Returns the cluster's physical layout from the config file. Layout loading makes
no occupancy query; the route's authentication guard still accesses the database.

### Request

| Parameter       | Location | Validation                                                                            |
| --------------- | -------- | ------------------------------------------------------------------------------------- |
| `clusterNumber` | Path     | `z.coerce.number().int().positive()` — see [Request validation](#request-validation). |

No query parameters or request body.

```bash
curl -b cookies.txt http://localhost:5001/api/clusters/1/layout
```

### Success response

Status: `200 OK`

```json
{
  "cluster": { "id": "c1", "number": 1, "label": "Cluster 1" },
  "rows": [
    {
      "id": "c1r6",
      "number": 6,
      "label": "R6",
      "cells": [
        {
          "kind": "place",
          "id": "c1r6p1",
          "number": 1,
          "position": "bottom"
        },
        { "kind": "place", "id": "c1r6p2", "number": 2 },
        { "kind": "gap" }
      ]
    },
    {
      "id": "c1r1",
      "number": 1,
      "label": "R1",
      "cells": [
        { "kind": "place", "id": "c1r1p1", "number": 1 },
        { "kind": "gap" },
        { "kind": "place", "id": "c1r1p2", "number": 2 }
      ]
    }
  ]
}
```

Field meanings:

- `cluster` — `{ id, number, label }`, same shape as an entry from `GET /api/clusters`.
- `rows[]` — rows in top-to-bottom physical order: highest row number first. The highest row depends on the selected cluster; do not assume every cluster has R6. The frontend can render in array order without sorting.
- `cells[]` — positions in a row, in order. Each cell is one of:
  - `{ "kind": "place", "id", "number", "position"? }` — a real, numbered seat.
  - `{ "kind": "gap" }` — visual spacer; no `id`, `number`, or `position`.
- `position` — `"top"` | `"bottom"`, optional. If absent, the rendering layer takes the opposite of the nearest preceding non-gap place in the same row. The first place in every row carries an explicit value in the config; interior places that continue the alternating pattern do not.

No `status`, no `peer` — occupancy belongs to `/occupancy`.

### Error responses

| Case                                          | Status | Code                    |
| --------------------------------------------- | -----: | ----------------------- |
| `clusterNumber` fails validation (e.g. `abc`) |    422 | `VALIDATION_ERROR`      |
| No cluster with that number in the config     |    404 | `CLUSTER_NOT_FOUND`     |
| Config file is unreadable or fails its schema |    500 | `INTERNAL_SERVER_ERROR` |

## `GET /api/clusters/:clusterNumber/occupancy`

Returns the currently occupied places. Every place not listed is free by implication. Requires a DB query.

### Request

| Parameter       | Location | Validation                                                                            |
| --------------- | -------- | ------------------------------------------------------------------------------------- |
| `clusterNumber` | Path     | `z.coerce.number().int().positive()` — see [Request validation](#request-validation). |

No query parameters or request body.

```bash
curl -b cookies.txt http://localhost:5001/api/clusters/1/occupancy
```

### Success response

Status: `200 OK`

```json
{
  "occupied": [
    {
      "row": 1,
      "place": 2,
      "peer": {
        "intraName": "jdoe",
        "displayName": "John Doe",
        "photo": null
      }
    }
  ],
  "lastUpdated": "2026-08-27T10:00:00.000Z"
}
```

Field meanings:

- `occupied[]` — one entry per occupied place. Places absent from this array are free.
  - `row` — row number within the cluster; matches `rows[].number` from `/layout`.
  - `place` — place number within that row; matches `cells[].number` from `/layout`.
  - `peer` — `{ intraName, displayName, photo }`, all fields `string | null`. Both name fields are passed through raw from the DB; no fallback or priority logic is applied server-side. Presentation is the frontend's decision.
    - `intraName` — Hive/intra login, nullable in the response type. The current DB schema requires a non-null login on the holder's Hive identity; guest occupancy without that identity is not represented by the current schema.
    - `displayName` — account display name, or `null` if absent; the API does not verify that it is a real name.
    - `photo` — avatar URL, or `null`; frontend uses an initial or `?` fallback when null.
    - **The response type permits all three fields to be `null`.** Render such an entry as occupied even without identity details. The current DB constraint requires occupied positions to have a holder and taken time; an occupied position without a holder is not a valid current database row.
  - No `email` — explicitly excluded per privacy rules.
- `lastUpdated` — ISO 8601 timestamp generated after the successful DB read.
  The shared type permits `null`, but this endpoint returns a timestamp on
  success and an error on read failure; it does not return an unread snapshot.

### Occupancy data source

Occupancy is read by `apps/api/src/features/clusters/clusters.repository.ts` using the shared `@repo/db` client. It queries occupied positions and matches config `id` to database `cluster.name`. Auth writes use the same client, so read-only connection permissions and production-source integration are not enforced by this repository.

### Error responses

| Case                                          | Status | Code                    |
| --------------------------------------------- | -----: | ----------------------- |
| `clusterNumber` fails validation (e.g. `abc`) |    422 | `VALIDATION_ERROR`      |
| No cluster with that number in the config     |    404 | `CLUSTER_NOT_FOUND`     |
| Production DB unavailable                     |    500 | `INTERNAL_SERVER_ERROR` |

## `GET /api/clusters/:clusterNumber/config-validation`

Checks whether the layout config is consistent with what the database currently reports.

The config file is structurally valid by construction — Zod catches schema problems at load time. This endpoint detects semantic mismatches: if the database returns occupancy for a `(row, place)` pair that doesn't exist in the config, the config is probably out of date. The current web map does not call this endpoint or populate its warnings array yet.

### Request

| Parameter       | Location | Validation                                                                            |
| --------------- | -------- | ------------------------------------------------------------------------------------- |
| `clusterNumber` | Path     | `z.coerce.number().int().positive()` — see [Request validation](#request-validation). |

No query parameters or request body.

```bash
curl -b cookies.txt http://localhost:5001/api/clusters/1/config-validation
```

### Success response

Status: `200 OK`

When the config and DB agree:

```json
{ "clusterNumber": 1, "valid": true, "errors": [] }
```

When the DB returns occupancy for a place the config doesn't know about:

```json
{
  "clusterNumber": 1,
  "valid": false,
  "errors": [
    {
      "code": "ORPHANED_OCCUPANCY",
      "message": "DB record for row 2, place 5 has no matching place in the layout",
      "path": "clusters[0]"
    }
  ]
}
```

- `valid: false` means the DB returned occupancy the config cannot account for. The database is the source of truth; the config is what's likely wrong.
- `errors[].code` — `ORPHANED_OCCUPANCY` is the only code currently produced.
- `errors[].message` — human-readable description of the mismatch.
- `errors[].path` — the cluster's position in the config file's `clusters` array.

### Error responses

| Case                                          | Status | Code                    |
| --------------------------------------------- | -----: | ----------------------- |
| `clusterNumber` fails validation (e.g. `abc`) |    422 | `VALIDATION_ERROR`      |
| No cluster with that number in the config     |    404 | `CLUSTER_NOT_FOUND`     |
| Production DB unavailable                     |    500 | `INTERNAL_SERVER_ERROR` |

## `GET /api/clusters/:clusterNumber/events`

A [Server-Sent Events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events) stream that delivers changes detected by the server polling PostgreSQL. Each subscribed cluster has one poller per API process, with a 30-second delay between completed poll cycles. One connection per cluster per client; one-directional (server → client only).

### Load sequence

Fetch `/layout` and `/occupancy` to construct the map. The web client opens
SSE after a successful occupancy response so loading and error states stay
with that request; it loads layout independently and may open SSE before
layout finishes.

Every new connection, including a reconnect, first receives a full
`occupancy-snapshot`, then `occupancy-delta` events relative to it. The
poller owns its per-cluster baseline: `/occupancy` is read-only and never
changes what the stream diffs against, and a new subscriber never resets the
baseline of existing ones. The baseline is dropped when the last subscriber
for a cluster disconnects.

```
GET /api/clusters/:clusterNumber/layout    → render the grid
GET /api/clusters/:clusterNumber/occupancy → mark initially occupied seats
GET /api/clusters/:clusterNumber/events    → receive a snapshot, then deltas
```

### Request

| Parameter       | Location | Validation                                                                            |
| --------------- | -------- | ------------------------------------------------------------------------------------- |
| `clusterNumber` | Path     | `z.coerce.number().int().positive()` — see [Request validation](#request-validation). |

No query parameters or request body. The browser's `EventSource` API sets `Accept: text/event-stream` automatically.

```bash
# curl example — streams indefinitely
curl -N -b cookies.txt -H "Accept: text/event-stream" http://localhost:5001/api/clusters/1/events
```

### Response — stream open

Status: `200 OK`  
Headers: `Content-Type: text/event-stream`, `Cache-Control: no-store`, `Connection: keep-alive`

All events are named so the client can use `addEventListener` rather than `onmessage`:

```js
const source = new EventSource("/api/clusters/1/events", {
  withCredentials: true,
});
source.addEventListener("occupancy-snapshot", (e) => {
  /* ... */
});
source.addEventListener("occupancy-delta", (e) => {
  /* ... */
});
source.addEventListener("error", (e) => {
  /* ... */
});
```

#### `occupancy-snapshot`

The full current occupancy, in the same shape as the `/occupancy` response.
Replace local occupancy with it. Sent:

- first on every connection: immediately when the cluster's poller already
  has a baseline, otherwise as soon as a poll started for the connection
  completes;
- to every connection on the first successful poll after a `DB_UNAVAILABLE`
  error, even if nothing changed, so clients can clear stale state.

```
event: occupancy-snapshot
data: {"occupied":[{"row":1,"place":2,"peer":{"intraName":"jdoe","displayName":"John Doe","photo":null}}],"lastUpdated":"2026-08-27T10:00:00.000Z"}

```

`lastUpdated` is the time of the poll that produced the baseline, so a
snapshot served from memory can be up to one poll interval old; any change
since then arrives as a delta.

#### `occupancy-delta`

Sent when occupancy changed since the last poll. Not sent when nothing changed.
A delta is never sent to a connection before its snapshot.

The stream carries incremental changes with explicit `occupied` and `freed` arrays, relative to the last snapshot plus the deltas since. It does not include event IDs or replay history.

```
event: occupancy-delta
data: {"occupied":[{"row":1,"place":2,"peer":{"intraName":"jdoe","displayName":"John Doe","photo":null}}],"freed":[{"row":1,"place":5}]}

```

| Field        | Meaning                                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `occupied[]` | Places that became occupied, or places already occupied whose peer data changed. Same shape as entries from `/occupancy`. |
| `freed[]`    | Places that were occupied and are now free. Identified by `{ row, place }` only — no peer data because the seat is empty. |

Apply a delta by removing entries in `freed`, then upserting entries in `occupied`. An event where both arrays are empty is never sent.

#### `error`

Sent when the database is unreachable during a poll cycle. The connection stays open.

```
event: error
data: {"code":"DB_UNAVAILABLE","message":"Occupancy data temporarily unavailable"}

```

On repeated `DB_UNAVAILABLE` events: keep the last successful occupancy rendered and mark it stale, showing the last successful update time. Do not clear occupancy and do not treat missing data as free. The server sends an `occupancy-snapshot` once the database recovers, which clears stale state even when recovery produces no changes.

A connection opened while the database is unavailable receives `error` events instead of a snapshot until a poll succeeds.

#### Keepalive comments

A comment line is sent every 20 seconds after a successful session recheck to prevent proxies from closing idle connections. Comments are invisible to `EventSource` handlers and require no client-side handling.

```
: keep-alive

```

### Reconnect

The server keeps no event history, so a client may miss changes while disconnected. The `occupancy-snapshot` that starts every connection repairs that state, so no `/occupancy` request is needed before reconnecting. The current client replaces browser automatic reconnect with this sequence:

1. On a native transport error, close EventSource, mark occupancy stale and check `/auth/session`. Stop retries on `401` or `403`.
2. Wait 30 seconds, then open a new credentialed EventSource. Repeat if it fails again.
3. Replace occupancy with the new connection's snapshot, which clears stale state.

The `Last-Event-ID` header sent by `EventSource` on reconnect is ignored — no event IDs are assigned.

### Error responses (before the stream opens)

| Case                                          | Status | Code                    |
| --------------------------------------------- | -----: | ----------------------- |
| `clusterNumber` fails validation (e.g. `abc`) |    422 | `VALIDATION_ERROR`      |
| No cluster with that number in the config     |    404 | `CLUSTER_NOT_FOUND`     |
| Config file is unreadable or invalid          |    500 | `INTERNAL_SERVER_ERROR` |

The common `401`/`403` access errors also apply before the stream opens.

Once the stream is open, database failures are delivered as `error` events rather than HTTP status codes.
