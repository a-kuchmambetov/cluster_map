# System Overview

Cluster Map is a pnpm monorepo with a React/Vite frontend, Express API,
Docusaurus documentation, a one-shot migration worker, and shared TypeScript packages.

## Implemented request path

1. The browser registers or signs in through the API. Better Auth persists
   accounts and sessions in PostgreSQL; new accounts need administrator approval.
2. An approved viewer loads the cluster list, layout, and occupancy. The API
   checks the session and current approval for cluster requests.
3. The API reads and validates `apps/api/src/config/clusters.json` for physical
   layout and uses Drizzle to query occupied positions and peer fields.
4. The frontend joins layout and occupancy by row/place number and calculates
   free, occupied, and total counts.
5. After the initial occupancy snapshot, an SSE connection delivers changes.
   One polling pool per cluster and API process queries PostgreSQL every 30 seconds
   while there are subscribers. Streams recheck access every 20 seconds.
6. Approved administrators list, approve, and delete users from `/admin/users`.
7. Viewers can sign in with GitHub or configure TOTP at `/settings/security`.

Public `/privacy` and `/terms` pages sit outside the protected route guard and
display draft notices even when the API is unavailable. Public API probes are
`/api/health` for database connectivity and `/api/health/ready` for auth
configuration, selected schema checks, and auth initialization.

## Component responsibilities

| Component            | Responsibility                                                                                                                         |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Web                  | Authentication screens, route guards, cluster map, place details, summaries, stale indicators, security settings, and user management. |
| API                  | Session/role enforcement, auth operations, layout validation, occupancy reads, SSE delivery, health checks, and request logging.       |
| Worker               | Database connectivity retries, migrations, and optional initial admin creation; exits after completion.                                |
| Database package     | Shared PostgreSQL client, auth/Hive Drizzle schemas, and migrations.                                                                   |
| Layout configuration | Cluster/row/place identity, physical order, staggered positions, and gaps.                                                             |
| Docs                 | Product, architecture, setup, reference, and operational guidance.                                                                     |
| Nginx                | Static web/docs hosting; API routing must be supplied externally or via a frontend API origin.                                         |

## Deployment boundaries

`docker-compose.dev.yml` runs PostgreSQL, the migration worker, API, web, and docs
using `Dockerfile.dev` without Infisical; the simulator is an optional profile.
Production apps have Dockerfiles inside their app directories. GitHub Actions
publishes selected images to GHCR and triggers Coolify; API/worker entrypoints
load runtime secrets from Infisical. The documentation site is configured for
`https://docs.map-hive.pp.ua/`.

## Architectural boundaries

- Browsers access PostgreSQL through the API.
- Layout and live occupancy remain separate API responses; the frontend merges them.
- Map routes read occupancy. Auth routes write accounts and sessions through the
  same DB client. A globally read-only database connection is not implemented.
- Snapshot refresh failures preserve previously loaded map data for that cluster.
- Production source permissions and deployment hardening remain release work.
